# 회부 — 부패 곡선 · 보존 가공의 다음 층 (2026-08-31)

이 배치(`server/spoil.js` 신설 · 부패 곡선 + 말리기·훈제·절임)에서 **구현하지 않고 넘긴 것들**과,
**재민의 판단이 필요한 것들**이다. 지시서 §5 가 지정한 회부 6건 + 실측 중 나온 4건.

> 규약: 여기 적힌 것은 **구현하지 않았다.** 그리고 조용히 정한 수는 나중에 아무도 못 고치므로,
> 이 배치가 스스로 유도한 값도 전부 아래 E 에 적어 둔다(무게 배치 B-3 의 선례).

## ★★A. 소금이 이 세계에 없다 — 절임이 걸려 있다 【가장 급하다】

**지시서의 전제가 현행 코드에서 성립하지 않는다.** 지시서는 이렇게 적었다:

> *"소금이 처음으로 쓸모를 얻는다(사건 장부 단골 부족 품목 — 캐러밴 지연 시 절임을 못 담그는
> 것까지가 의도된 연쇄)."*

실측 결과 소금은 **단골 부족 품목이 아니라 아예 없는 물건**이다:

| 층 | 소금의 지위 | 근거 |
|---|---|---|
| specialty 카탈로그 | **있다** — `salt {ko:'소금', category:'mineral', weight:1.0, baseValue:5, harvest:'mining'}` | `server/specialty.js:54` |
| 한반도 광종 배분 | **없다** — POOL 8종(철·구리·금·납·옥·은·흑요석·주석)에 소금 없음 | `server/hanbando-minerals.js` |
| specialty 바이옴 목록 | desert·savanna·archipelago 에만 | `specialty.js:733,739,740` — 한반도 존의 바이옴이 아니다 |
| econ v2 재고 | 산출이 없으니 **재고도 0** | specialty 197종은 TRADABLE 로 통합되지만 산출 경로가 없다 |
| 플레이어 대응표 | **없다** — `PV_DEPOSIT_MAP` 에 소금 없음 | `server/villages.js:3394` |
| 게시판·거래소 | **못 다룬다** | `events.buildDeliverable` 이 그 표에서 파생된다 |
| 사건 장부 한글 이름 | 있다 — 그런데 그 줄 위에 *"표시 전용이다(경제 로직 아님)"* | `server/events.js:47,57` |

⇒ **절임을 지금 그대로 열면 영원히 못 만드는 레시피가 된다.**

### 이 배치의 처리
말리기·훈제는 완전 구현. **절임도 레시피·시설·게이트·하네스까지 전부 구현했다**(하네스가
소금을 주입해 검증 — `test-preserve ④ⓐ`). 빠진 것은 **세계가 소금을 내주는 경로 하나**뿐이다.
"반쪽 구현보다 이월"(절대 규칙 7)의 뜻대로, **기계는 완성하고 입력만 이월**했다.

### 권고안 — 자염(煮鹽): 화덕에서 바닷물 졸이기

세 가지를 다 만족하는 유일한 안으로 보인다:

1. **고증** — 청동기~삼국 한반도의 실제 제염법이 자염(바닷물을 끓여 소금을 얻는 것)이다.
   암염 광산은 한반도에 없다. 광맥을 까는 안은 고증 위반이고, `hanbando-minerals.js` 가
   이미 기각한 "실제 산지 지도" 논쟁을 다시 여는 일이다.
2. **배선이 이미 있다** — 배산임수 캐논으로 마을은 물가에 있고, 바닷물 판정은 지형 정본에 있다.
   "제작창 = 시설의 창" 문법에 화덕 레시피 한 줄로 얹힌다(**새 시설 0 · 새 개념 0**).
   보존 3종이 쓰는 그 `Spoil.PRESERVE` 표에 항목 하나를 더하면 끝이다.
3. **연쇄가 살아난다** — 소금이 노동의 산물이 되면, 지시서가 그리던 "소금이 없어 절임을 못
   담근다"가 **캐러밴이 아니라 내 일정** 때문에 성립한다. 더 좋은 압박이다.

### 대안 두 개(권고 아님)
- **ⓑ `PV_DEPOSIT_MAP` 에 `salt:'salt'` 한 줄** — 곡물 품목화의 그 한 줄과 같은 수법이라
  게시판·거래소가 특별 취급 코드 없이 소금을 다루게 된다. 다만 **마을 재고가 0 이면 아무 일도
  안 일어나고**, 오히려 소비EMA 0 인 재화가 부족 판정에 들어가 게시 건수 기준선을 흔들 수 있다.
  ⚠**게시 건수 기준선은 이런 한 줄에 실제로 움직인 전례가 있다**(곡물 품목화: 1,561/1,487/1,535
  → 1,647/1,583/1,679). 넣는다면 **단일 손잡이 A/B** 로 그 이동을 먼저 재야 한다.
- **ⓒ 캐러밴 수입 전용 품목** — econ 을 건드려야 한다(무수정 캐논 위반). 기각 권고.

**재민 판단 필요: ⓐ 자염 / ⓑ 대응표 한 줄 / ⓒ 그 밖.**

## B. 온도 결합 부패 — 더운 날 빨리 상한다 【지시서 §5 지정】

구현 금지 지시대로 **안 했다.** 붙일 자리는 한 줄이고 이미 비워 뒀다:

```js
// server/spoil.js — freshnessOf 안
const L = shelfOf(item) / tempMult(temperatureAt(day));   // ← 이 한 줄
```

★**반드시 추위 2차 트랙과 같은 온도 정본**(`weather.temperatureAt` — econ 기온에서 유도한
연속 곡선)을 읽어야 한다. 지금 두 벌로 만들면 그게 사본이고, 겨울 난이도와 부패가 **다른 겨울**을
보게 된다. 그래서 추위 2차가 착지한 **뒤에** 붙이는 것이 맞다.

부수 효과가 큰 층이다: 여름에 생선이 이틀이 아니라 하루면 상하면 **말리기가 계절 노동**이 된다
(그게 원래 청동기의 여름이다). 반대로 겨울엔 곳간이 냉장고가 되어 보존 압박이 낮아진다 —
겨울나기 산수(§아래 대리 지표)가 그만큼 물러진다. **수치는 그때 다시 재야 한다.**

## C. 저장 시설 = 부패 감속 【지시서 §5 지정 · 근거를 찾았다】

★**지어낼 필요가 없다 — econ 에 이미 있다.** `sim/economy-sim-v2.js` 의 옹기(장독):

```js
const CLAY_DAILY_PC = 0.02;        // 1인당 일일 진흙(가구 장독 빚기)
const POTTERY_DECAY_SAVE = 0.3;    // 완전 충족 시 부패 −30%(질그릇 밀폐 — 상한)
```

NPC 마을은 **진흙을 소비해 장독을 유지하고, 그 대가로 부패성 식량의 부패율이 최대 30% 낮아진다.**
플레이어 층의 "움·곳간·장독"은 이 상수에서 **유도**하면 된다(옮겨 적지 말 것 — `POTTERY_DECAY_SAVE`
를 읽어라). 그러면 플레이어의 저장고와 NPC의 장독이 **같은 물리**를 갖는다.

건축과 함께 가야 하는 층이라 이번엔 안 했다. 붙일 곳: `Spoil.freshnessOf` 가 보관 맥락을 인자로
받는 형태(`freshnessOf(item, ageDays, {storage})`) — 지금 시그니처가 그걸 받아들일 수 있게 열려 있다.

## D. 취득일 = **완성일**로 잡았다 — 요리와 다르다 【확인 필요】

보존 산출의 로트 취득일을 **완성일**(`doneAt`)로 잡았다. 요리는 **꺼낸 때**(`craftedAtMs`)다.
같은 레포 안에 두 규약이 생겼으니 알고 넘어가야 한다.

- **왜 다르게 잡았나**: 요리 대기열은 20초라 "언제부터 세느냐"가 무의미하다. 보존은 **며칠**이다.
  수령일로 잡으면 **건조대가 무한 정지 상자**가 된다 — 걸어 두면 안 상하는 창고. 그러면
  "말렸으면 가져가라"가 없어지고, 보존식이 아니라 마법 상자가 된다.
- **대가**: 며칠 뒤에 받으러 가면 그만큼 이미 늙어 있다(하네스 `③ⓓ` 가 그걸 못 박는다).
  "가마는 밤새 탄다"는 진행에 관한 말이지 **보관**에 관한 말이 아니라는 게 이 배치의 해석이다.
- **뒤집으려면**: `doCraftCollect` 의 `j.lotItems` 분기에서 `_gameDayAt(j.doneAt)` 를
  `zoneGameDay()` 로 바꾸면 된다(한 줄). 하네스 `③ⓓ` 도 같이 뒤집어야 한다.

## F. 구현 금지 — 그대로 지켰다 【지시서 §5】

- **식중독 확률 모델 — 금지.** 확정 탈로 갔다. 하네스가 **20회 반복해 같은 값**임을 못 박는다
  (`test-preserve ②ⓒ`). 나중에 누가 확률을 넣으면 그 검사가 먼저 깨진다.
- **술 빚기** — 안 했다.
- **겨울나기 공동 비축 UI** — 안 했다(마을 프로젝트 층).
- **보존식 econ 편입** — 안 했다. 현재 `dried_fish` 등은 **플레이어 층 품목**이고
  `PV_DEPOSIT_MAP` 에 없어 **거래소·게시판이 취급하지 않는다**(그래서 econ 지표가 안 움직인다).
  편입하려면 A-ⓑ 와 같은 문제를 안는다: 대응표 한 줄이면 배선은 끝이지만, **게시 건수 기준선이
  움직인다.** 단일 손잡이 A/B 선행 필요.

## G. 이번 층에서 나온 작은 것들

- **G-1. 보존식 품질 등급 축** — "시든 재료 → 하급 산출"을 **수율**(개수)로 표현했다.
  로트 레코드가 `{d, n}` 둘뿐이라 품질 축을 얹으려면 저장 형식·UI·거래소가 다 움직인다.
  등급이 정말 필요하면 그때 `player-items` 인스턴스 문법(요리 `dish` 처럼)을 쓰는 쪽이 맞다.
- **G-2. 보존 수량 선택** — 제작창의 "만들기"는 **한 번에 한 단위**다(요리와 같은 규약).
  사흘짜리 공정을 한 개씩 거는 건 손이 많이 간다. 서버 `doPreserve(player, recipe, amount)` 는
  **이미 수량을 받는다** — UI 만 얹으면 된다. 새 패널 없이 붙일 자리를 찾는 게 판단.
- **G-3. 건조대 스프라이트** — 지금은 **벡터 발판 도형**이다(작업대와 같은 처지).
  Blender `icon_render.py` 로 뽑아 `ICON_NO_RENDER` 에서 빼면 된다.
- **G-4. econ 과 플레이어 층의 부패 순서가 반대다 — 해석을 박제한다.**
  econ: 생선·고기 0.0005 < 조리식 0.001 < 채소 0.0015 (**생선이 가장 느리다**).
  플레이어: 생선 2.5일 < 조리식 3.5 < 채소 6 (**생선이 가장 빠르다**).
  모순이 아니라 **층이 다르다**: 곳간에 쟁인 생선은 이미 말리거나 절인 생선이고(그래서 오래 간다),
  플레이어의 로트는 방금 잡아 손에 든 생선이다. **보존 가공이 두 층을 잇는 다리**이고,
  건어물 보관일(45일)이 econ 쪽 스케일에 가깝게 잡힌 이유가 이것이다.
  ⇒ 나중에 누가 "두 표가 안 맞는다"고 고치려 들 때 **이 문단이 답이다.** 맞추면 안 된다.
