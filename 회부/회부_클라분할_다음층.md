## A. 무엇이 깨졌나

지시서의 근거는 이랬다:

> *"classic `<script>` 여러 개는 최상위 `function/const/let` 을 **같은 전역 렉시컬 스코프에서
> 공유**하므로, 자르기만 하면 함수 간 참조는 그대로 산다."*

**맞는 말이다. 다만 `client.js` 의 함수들은 최상위가 아니다.**

```
  실측 (node scripts/split-audit.js public/client.js)

    파일 15,946줄
      L   5– L  54   진짜 최상위 — 배너 · 상수 몇 개 · 함수 1개        (문장 13개)
      L  56– L15245  ★(() => { … })()   ← 15,190줄. 클라 거의 전부가 이 안이다
      L15250– L15945   (() => { … })()   ←    696줄

    그 큰 IIFE **안** 깊이1:  문장 874 · function 선언 **301** · 선언 이름 822 · 실행문 141
```

PM 이 잰 "최상위 함수 301개"가 바로 **이 IIFE 안 깊이1** 이다. 즉 파일은 평평하지 않고
**클로저 하나**다. 그래서 함수 경계에서 잘라 여러 `<script>` 로 나누면:

1. 조각마다 괄호·중괄호가 안 맞아 **문법 오류**다(`node --check` 에서 바로 죽는다).
2. 억지로 각 조각을 다시 `(() => { … })()` 로 감싸면 이번엔 조각들이 **서로 다른 클로저**가
   되어 함수 간 참조가 통째로 끊긴다 — 이건 분할이 아니라 파괴다.

⇒ **"자르기만 하면 된다"가 이 파일엔 적용되지 않는다.** 그래서 멈췄다.

## B. 길 넷 — 전부 **설계 판단**이라 구현하지 않았다

### ⓐ IIFE 껍데기를 벗기고 나서 자른다 ★가장 싸다
`(() => {` 와 `})();` **두 줄을 지우면** 822개 이름이 진짜 최상위로 올라오고, 그 다음엔
지시서가 그린 분할이 **글자 그대로** 성립한다.

```
  실측한 위험 — 껍데기를 벗겼을 때 무엇이 부딪히나
    · 다른 클래식 스크립트(terrain-gen/terrain/soil-base/move-model/animals)의
      최상위 이름 60개와 **충돌 0**  (822개 전수 대조)
    · 브라우저 전역(name·status·length·top·closed·event…)과 **충돌 0**
    · 최상위 `this` 는 전후 모두 `window`(클래식 스크립트의 화살표 IIFE라 그대로 상속) — 변화 없음
    · `'use strict'` 없음 → strict 전환 없음
```
그래도 **행동 변경 0 은 아니다**: `function` 선언 301개가 `window` 프로퍼티가 되고
(`let/const` 는 전역 렉시컬로 가서 `window` 엔 안 붙는다), 앞으로 이름 충돌의 여지가 생긴다.
"한 글자도 바꾸지 마라"에 걸리므로 **재민 판정 없이는 못 한다.**

★자른 뒤 필요한 후속 작업도 이미 재 뒀다:
```
  실행문 141개 중 **자기 뒤에 선언된 이름을 참조하는 것 26개** (뒤 참조 62건)
  ⇒ 분할하면 이 26개만 마지막 조각(99-main.js)으로 옮기면 된다(원문 순서 유지).
     나머지 115개는 제자리에 둬도 된다.  ← 생각보다 작다
```
(전수는 `node scripts/split-audit.js public/client.js --list`)

### ⓑ 소스는 나누고 **결합해서 서빙**한다 ★행동 변경이 증명 가능한 0
`public/client/00-*.js … 99-*.js` 로 나눠 두고, 서빙(또는 빌드) 시 **이어 붙여** 지금과
**바이트 동일한** `client.js` 를 만든다. IIFE 를 건드리지 않으므로 스코프가 그대로다 —
결합 diff 가 `identical` 이면 행동 변경이 **증명된 0** 이다.
⚠대신 **빌드/서빙 단계**가 생긴다(지시서가 회부로 뺀 항목). 정적 서빙 규약과 캐시버스터도 같이 정해야 한다.

### ⓒ ES 모듈 전환
지시서가 이번 층에서 명시적으로 금지했다. 스코프·hoisting·strict 가 다 바뀐다.

### ⓓ 그대로 둔다
분할의 목적은 "여러 세션이 같은 파일을 덜 만지게"인데, 이번 배치의 **작업②·③만으로도**
인계 문서와 러너라는 큰 충돌 지점 둘이 사라졌다. 클라 분할은 그 다음 순위여도 된다.

★내 관찰: **ⓐ가 이번 층의 답**이다 — 충돌 0 이 실측으로 확인됐고, 이사할 실행문도 26개뿐이다.
다만 "껍데기 두 줄 제거"는 명백한 행동 변경이라 **재민이 그 두 줄을 허락해야** 시작된다.
ⓑ는 증명 가능성이 가장 높지만 빌드 단계라는 새 층을 연다.

## C. 이번 배치가 남긴 것 (다음 층이 그대로 쓴다)

* `scripts/split-audit.js` — 최상위 실행문 감사기.
  IIFE 로 감싸인 파일을 **먼저 알아보고 경고**한다(그게 이 회부를 만든 도구다).
  `--list` 로 "뒤 참조 실행문" 전수, `--json` 으로 기계 판독.
  ⇒ 껍데기를 벗기기로 하면 이 도구가 그날 바로 이사 목록을 낸다.

* `scripts/split-verify.sh`(결합 diff 검사기)는 **안 만들었다.** 검증할 분할이 없는데
  검사기만 먼저 쓰면 **한 번도 통과·실패를 보여 준 적 없는 코드**가 레포에 남는다
  (이 레포가 여러 번 배운 것: 하네스가 먼저 틀린다 — 돌려 보지 않은 하네스는 하네스가 아니다).
  ⇒ 분할을 실제로 하는 배치에서, **일부러 한 글자 바꾼 조각이 `differ` 를 내는지** 먼저 확인하며 같이 만든다.
