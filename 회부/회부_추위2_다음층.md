## B. 판단거리 (재민 확인 필요)

### B-1 ★"조잡한 베옷 warmth 8" 을 **표시값이 아니라 문턱으로** 이뤘다 — 확인 요청
```
  지시: "조잡한 베옷(맨손 제작, warmth 하향 — 시작점 8)"
  현행: 맨손 삼베옷의 표시 방한은 **15 그대로**, 대신 `BODY_WARMTH_MIN = 10` 아래는 단열 0 이라
        실효 단열이 **+0.45℃** 뿐이다 ⇒ 한겨울 야생 밤 12/24(≥50%) — 지시한 판정 그대로.
  이유: ① `attrScale` 을 낮추면 기존 저장 아이템과 어긋난다(위 A)
        ② 문턱(WARMTH_MIN)은 **디에게틱**이다 — 헐거운 홑옷은 여미지 못해 바람이 지나간다
        ③ 표시는 `displayItem` 이 "삼베옷 [방한 15]" 로, 배지 툴팁이 "체감 +0.45℃" 로 **둘 다** 말한다
```
★그래도 표시값 자체를 8 로 낮추고 싶다면: `ITEM_TYPES.clothes.attrScale` 62→33 + `WARMTH_C_PER`
0.09→0.17 + `WARMTH_MIN` 10→5.3 이면 **같은 사다리**가 나온다(비례라 판정 불변). 저장 마이그레이션만 붙이면 된다.

### B-2 ★★고도 감률은 살렸는데 **세계가 낮다** — 산이 안 추운 진짜 이유
```
  실측(같은 한겨울 자정 · 야생 맨몸):
      0km   목표 0.928 → 안 옴      ← 지금 플레이어가 설 수 있는 유일한 고도
   0.035km  목표 0.935 → 안 옴      ← ★산 높이 캐논 35m. 기여 0.007. 사실상 0.
   0.25km   목표 0.977 → 10.0분
   0.5km    목표 1.025 →  5.8분
      1km   목표 1.123 →  4.0분
      2km   목표 1.318 →  2.7분
  ⇒ 모델은 **살아 있다**(단조 · `test-body ⑮㉢`). 막는 건 둘:
     ① 산 높이 캐논이 **35m** 다(client.js:2514 "산 높이 35m 확정") — 감률로는 0.23℃.
     ② 바위 셀은 **통행 불가**다(Phase 5-H) — 애초에 산 위에 설 수가 없다. 고개는 산을 뚫는 길이라 고도가 아니다.
  ⇒ 그래서 `elevKmAt()` 은 지금 **언제나 0** 을 낸다. 없는 고도를 지어내지 않았다.
```
길 셋:
· ⓐ **산 높이 캐논을 올린다**(35m → 300~800m). 산 아크의 렌더·가림·자락 계산이 전부 그 수를 쓴다
  ⇒ **산 아크 배치의 일**이지 추위 배치의 일이 아니다.
· ⓑ **걸을 수 있는 고지를 만든다**(능선길·고원). 지형 배치.
· ⓒ **고도 말고 노출로 말한다** — 바위·능선은 바람이 세다는 별도 항(디에게틱, 새 손잡이).
★내 관찰: **ⓒ가 이번 층의 답**이다(싸고, "산은 춥다"가 바로 선다). ⓐ·ⓑ는 산 아크 소유자 판단.

### B-3 장인이 지은 삼베옷은 **꽤 좋다** — 의도인가
```
  맨손 삼베옷(Lv0)        방한 15 → +0.45℃ → 한겨울 야생 밤 12/24
  장인 삼베옷(마을 EMA 0.8) 방한 31~37 → +1.9~2.4℃ → 사실상 가죽옷 급
```
`materializeFromVillage` 가 마을 품질 EMA 로 **대표 숙련 Lv7~10** 을 역산하기 때문이다(종전 규약).
"겨울 = 가죽·모피 수요"라는 축을 세우려면 **재료가 숙련을 이기게** 해야 할 수도 있다.
· ⓐ 그대로 둔다 — "좋은 장인은 삼베로도 잘 짓는다"는 말이 된다(현행).
· ⓑ 옷만 재료 가중을 키운다(숙련 span ↓ · 재료 span ↑). `MAT_GRADE` 는 못 건드리니 옷 전용 가중.
★econ 접점은 없다(플레이어 층 전용). 다만 거래소 가격은 econ 이 정하므로 **값과 성능의 정합**은 별건이다.

### B-4 겨울의 위험은 아직 "느려짐"뿐 — 죽음 설계 대기
천장을 열어 **속도**는 갈렸지만(5.2~10.6분) 3단계 추위는 여전히 이속 ×0.85 · 작업 ×0.80 이다.
동사(凍死)는 아사·탈수사와 **한 묶음**으로 죽음 설계 배치에서. (튜닝1·온도 배치 회부 그대로 이월.)

### B-5 `살을 에는 추위` 칸이 생겼다 — 이름 확인
천장 해제로 1 초과 구간이 생겨 라벨을 하나 더 뒀다(1.05 초과). 맨 윗칸을 **'살인적'이라 부르지 않았다** —
추위는 아직 HP 를 안 깎으므로 화면이 죽음을 약속하면 거짓말이 된다. 이름은 재민 취향 확인 대상.

### B-6 `perf-pair` 기준선은 **사람이 올린다**
`scripts/perf-baseline.json` = `d01074a4`(온도 배치 직전). 자동 갱신하면 기준선이 늘 HEAD 라
**자기 자신과의 비교 = 자명 통과**가 된다. 그래서 HEAD == 기준선이면 도구가 비교를 **거부**한다.
⇒ 성능에 영향 있는 배치를 넘길 때마다 **의도적으로** 올려라(그 커밋이 새 기준선이 된다).

### B-7 러너에 성능 짝 비교를 넣을 것인가
`perf-pair` 는 판당 하네스를 4번(≈16분) 돌린다. 러너에 넣으면 회귀 한 바퀴가 그만큼 길어진다.
⇒ 지금은 **계측기**로 뒀다(러너 미등록). "성능을 건드린 배치에서만 사람이 돌린다"가 현행 규약.
러너에 넣으려면 라운드 수를 줄이거나(정밀도 ↓) 야간 배치로 분리해야 한다.

### B-8 `e2e-mtfoot ⑤` — 여전히 깨져 있다(이 배치 무관)
온도 배치에서 A/B 로 확인한 그대로(`HEAD 0.34/0.45/72% = BASE`). 산 기슭 기하 문제.
이번 배치도 지형을 한 줄도 안 건드렸다. **산 아크 소유자 판단.**
