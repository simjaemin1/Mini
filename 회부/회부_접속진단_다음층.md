## B. 실측으로 드러난 판단거리 (재민 확인 필요)

### B-1 ★★기존 하네스 다수의 입장 게이트가 **자명 통과**다
```js
  !(await page.evaluate(() => !!(window.__getMyAbs && window.__getMyAbs())))
```
`let myAbsPredicted = { x: 0, y: 0 };` 로 시작하므로 **언제나 참**이다 — 이 관용구는
"입장했는가"를 **한 번도 재지 않았다**. `e2e-conn` ②에서 "확정 오류인데 true" 로 잡혔다.
· 이번 배치는 `window.__inWorld()`(welcome 수신 여부)를 새로 내고 **`e2e-conn` 만** 그걸 쓴다.
· 기존 하네스들은 뒤따르는 `sleep(2200)` 덕에 실제로는 통과해 왔다 — **판정만** 무의미했다.
★판단거리: 일괄 교체할 것인가. 교체하면 **느린 판에서 실패가 드러날 수 있다**(지금은 sleep 이 가려 준다).
그게 좋은 일이지만 한 배치를 잡아먹을 수 있어 따로 뺀다. 대상: `__getMyAbs` 게이트를 쓰는 10여 종.

### B-2 ★마감액 30초가 맞는가
`CONN_DEADLINE_MS` 기본 30초. 클라 경고(20초)보다 뒤에 서게 잡았다 — 화면이 먼저 노랗게 말하고,
그래도 안 끝나면 서버가 이름을 붙여 끊는다.
★판단거리: 라이브 welcome 이 51마을·수천 건축물이라 **정상적으로도 오래 걸릴 수 있다**.
30초를 넘는 정상 입장이 있다면 마감액이 **멀쩡한 접속을 끊는다**. 실측이 필요하다:
라이브에서 `docker logs … | grep "접속 처리 시간 초과"` 가 뜨는지 며칠 보고 정한다.
※지금은 안전 쪽이다 — 끊겨도 백오프로 다시 붙고, 사유가 화면에 뜬다(조용한 실패가 아니다).

### B-3 ★`ping 후 15초` 좀비 판정이 이제 겹친다
조기 pong 이 생겼으므로, **입장 처리 중에도 pong 이 온다** → 15초 좀비 판정이 옛날처럼
"느린 입장"을 죽이지 않는다(개선). 다만 판정이 셋으로 늘었다:
15초 pong 미수신(좀비) · 20초 entering(화면 경고) · 30초 마감액(서버가 끊음).
★판단거리: 셋을 **한 축으로 정리**할 것인가. 지금은 각각 다른 실패를 재고 있어 겹쳐도 무해하지만,
숫자가 셋이면 다음 사람이 어느 것을 만져야 할지 헷갈린다.

### B-4 ★central 이 느릴 때의 갈래가 아직 이름이 없다
연결 핸들러의 `await` 는 전부 `central-client` 호출이고, 그 안에 **소켓 유휴 5초 타임아웃**이 있다.
그런데 그건 *유휴* 기준이라 "느리게 계속 보내는" 응답엔 안 걸린다. 마감액이 그걸 30초에서 잡지만
사유는 `단계 auth 에서 멈췄다` 로만 나온다 — **central 탓인지 zone 탓인지 구분이 안 된다**.
★판단거리: central 호출에 **총 소요 마감액**을 따로 걸고 사유를 `central 응답 지연` 으로 분리할 것인가.
(그러면 라이브에서 "central 이 병목"을 화면만 보고 알 수 있다.)

### B-6 ★★B-6 승계 경합 — 부하에서 몸을 놓친다 (**선재 결함 · 구조가 재민 확정이라 회부**)
`test-guest-rejoin` ②가 러너 안에서 간헐 실패한다. **부하 A/B 로 귀속을 갈랐다**:

```
  직전(f1659af) + CPU 2코어 부하 : ✓ / ✗(저장 좌표와 0px) / ✓
  지금(HEAD)    + 같은 부하      : ✓ / ✓ / ✓
```
이 배치가 만든 게 아니다. 기전은 경합이다:
· A 의 소켓 close 처리(**로컬 이벤트** — `attachPlayerHandlers` 의 close 가 `players.delete`)
· B 의 승계 스캔(`await central.guestIdentity` **뒤** — **HTTP 왕복**)
부하가 걸리면 central 왕복이 늘어져 **A 의 close 가 먼저 이긴다** → 승계할 몸이 없어 저장본으로 태어난다.
`_supersededBy` 는 *반대 방향*(옛 close 가 새 좌표를 덮어쓰는 것)만 막는다.

★판단거리 셋:
ⓐ **짧은 유예**(2~3초) 동안 끊긴 몸을 `players` 에서 지우지 않고 "승계 대기"로 붙잡는다.
   가장 확실하지만 **B-6 재민 확정 구조에 상태를 하나 더 넣는 것**이다(중복 로그인·저장 순서와 얽힌다).
ⓑ 승계 스캔을 **central 왕복 앞으로** 옮긴다(playerId 를 토큰에서 먼저 알 수 있는 경우만).
   경합 창이 거의 0 이 되지만, 게스트 토큰→playerId 해석이 central 에 있어 항상 되진 않는다.
ⓒ 그대로 둔다 — 실기 영향은 "재접속 시 몇백 px 되돌아감"이고, 이제 **조용하지 않다**
   (되돌아간 게 화면에 보인다). 라이브에서 실제로 거슬리는지 재민 판정.
※이 배치 뒤로는 최소한 **증상이 보인다** — 종전엔 같은 부류의 실패가 무한 침묵으로 나타났다.

## C. 이 배치가 바꾼 것 (다음 세션이 헷갈리지 않게)

· `wss.on('connection', async …)` → **동기 래퍼 + `_acceptConnection(ws, req, C)`**.
  본문은 그대로다(재들여쓰기 없음). `return` 은 전부 `_acceptConnection` 에서 나가는 것으로 뜻이 같다.
· 새 메시지 셋: `conn_hello` · `conn_error{ref,stage,msg}` · `pong` 에 `stage`·`ref` 추가.
· 새 env 셋: `CONN_DEADLINE_MS`(30000) · `E2E_CONN_FAIL`·`E2E_CONN_HANG`(둘 다 `E2E_GIVE=1` 전용).
· 클라: `handleDrop` 때처럼 배너 그리는 곳을 **하나로** 모았다 — `paintConnBanner()`.
  `setNetStalled` 는 이제 상태만 바꾸고 그리지 않는다.
· `#netLost` 는 `data-state`(waiting/entering/error/lost) · `data-hard`(0/1) 를 갖는다.
  **색과 문구는 `data-hard` 가 정한다** — 0=노랑(기다려라) · 1=빨강(오류).
· 새 읽기 훅: `window.__connState()` · `window.__inWorld()`.
