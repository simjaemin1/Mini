# T1481 진단 자료

`diagnose.cjs`는 Node 프리로드 관찰기다. `_compile`에서 대상 문자열이 정확히 한 곳인지 확인하고 메모리 속 사본에 계측을 주입한다. 제품 파일에는 쓰지 않는다. 최초 2날 스모크에서 관찰기 파일 쓰기의 스코프 오류를 발견해 수정했고, 그 실패 사본은 성능·세계 비교에서 제외한다. 수정본 스모크는 종료 코드 0이다.

`run-diagnosis.sh`는 현재 main 기준의 **새 세계**를 지정된 집 끔·캐러밴 몸 끔·가상 시계·6GB 힙·seed 42 조건으로 만든다. T1434 원본 세계의 저장본을 복구했다는 뜻이 아니다. 870날에 체크포인트를 남기고 872날까지 잇는다. 869날부터 관찰한다. `setsid nohup python3 -u 계측/T1481_2026-11-25/controller.py > <로그> 2>&1 < /dev/null &`로 실행한다. Python controller는 `subprocess.run`과 `finally`로 종료 코드·완료 표시를 남긴다. 완료 표시는 `$T1481_OUT/done`이며 기본 출력은 `/workspace/scratch/t1481-main870`이다. 체크포인트와 DB는 삭제하지 않는다. 첫 1~2분에는 생존을 확인하고 이후 10분마다 완료 표시와 런처·실제 존의 생존을 함께 본다.

최초 `nohup` 단독 실행(05:15:20Z)은 완료 표시 없이 끝났고 06:16Z 확인 때 런처가 zombie, 실제 러너·존이 없었다. 마지막 진행 기록은 05:16:20Z·econ 0이다. **종료 주체 미확인·실행 분리 실패 추정**이며 게임 OOM이나 T1481 진단 결과로 세지 않는다. 사본은 `/workspace/scratch/t1481-main870-detach-failed`에 분리했다. `setsid` Python controller 재시작은 06:17:18Z다.

## 분모

- `ticks`: 호스트 `tickWarBodies` 호출 수. 가상 시계에서는 하루 몫을 `_t681Flush`가 한꺼번에 메우므로 이것만으로 교전 한 스텝의 부담을 표현할 수 없다.
- `warTicks`: `_warTickOne` 호출 수. `callsPerWarTick`은 그 분모로 센 지킴 자리 호출 수다. `callsPerTick`도 함께 보존한다.
- `scans`: 실제로 존 나선에 들어가 막힘 술어를 호출한 방문 수다. 원점 재검사·같은 정수 칸의 중복 방문을 포함하고 캐시 적중의 방문은 0이다. `uniqueCells`는 별도 수다. `scansPerCall`의 분모에는 캐시 적중 호출도 포함한다.
- `blockedPct`: 방문 중 전쟁 막힘 술어가 참인 몫. `rockPct`: 같은 방문 중 존의 산맥 바위 정본 술어가 참인 몫. 물·환호·건물·나무와 산을 혼동하지 않는다. 산 분류는 관찰기 자체 정수 칸 메모에서 읽으며 원래 막힘 술어의 반환값은 그대로 돌려준다.
- `repeatPct`: 전쟁 ID·병사 pid가 식별되는 추종 호출(`identified`) 중, 정확한 실수 과녁과 막힘 세대가 같은 질문이 이미 관찰된 몫이다. pid를 식별하지 못한 호출은 분모에 넣지 않는다. 좌표를 반올림하지 않는다. 몸의 현재 위치는 자리 찾기 함수의 인자가 아니다.
- `cache`: 기존 T1349 캐시의 누적 hit·miss·size다. 새 T1481 캐시가 아니다.
- `day`: 호출을 집계한 세계 날. `snapshotDay`: 그 집계를 쓰는 순간의 세계 날이다. 다음 날 첫 틱이나 종료 순간에 쓰므로 교전 단면의 날과 집계 구간을 구분해야 한다. 재시작은 pid로 구별한다.

`historical-profile.json`은 원본 78,833개 CPU 표본을 함수별 자기·포함 표본으로 다시 센 값이다. 호출 수가 아니다. 원본 재계산 자는 `계측/T1434_2026-11-22/t1434-prof.js --file <압축 푼 cpuprofile>`이다. `historical-summary.json`의 868~881날은 선포·전투·사상·활성·몸·교전 **요약이 같은 구간**일 뿐, 전쟁 ID가 없는 자료로 같은 교전이라고 단정하지 않는다.

## 관찰기 분기 확인

2날 서버 스모크에는 교전이 없어 호출·나선 분기를 검증하지 못했다. 실제 서버를 추가로 띄우지 않고 기존 `WW_PART=march node scripts/test-war-world.js`를 프리로드로 실행해 7/0, 호출 12·방문 43을 확인했다. 이어 기존 `test-t1060-scram-hold.js`의 `T1060_SUB=war T1060_P='{"far":[0,0]}'` 전쟁 fixture로 교전 스텝·추종 병사 pid·반복·나선·JSON 쓰기를 확인했다. 고정 시각 판은 호출 1,617·교전 스텝 7,993·방문 7,990·식별 900·반복 899다. **이것들은 꾸민 장면의 관찰기 검증 수치이며 870날 측정값이 아니다.**

관찰기 유무를 비교할 때 시각을 고정하지 않은 최초 fixture 두 판은 결과가 갈렸다. 이 fixture는 스폰 때만 Date를 고정하고 나머지 정본 호출은 실제 `Date.now`를 읽는다. `node -e 'Date.now=()=>400*30000+1;require("./scripts/test-t1060-scram-hold.js")'`를 위 fixture 환경으로 두 번 실행하되 한쪽만 관찰기를 프리로드하면 전체 출력이 바이트 같다. 날짜·시간 고정은 이 합성 fixture 확인에만 사용하며, 진행 중인 870 재구성 판은 원래 지정한 가상 시계를 그대로 쓴다. 결과는 `observer-smoke.json`에 구분해 보존했다.
