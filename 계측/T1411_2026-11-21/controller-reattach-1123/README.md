# 실행 도구 재연결 뒤 살아 있는 세계의 감독 재접속

11월23일 실행 도구 재연결 때 두 세계의 래퍼·정본 러너·실제 존과 백업·최종 집계 프로세스는 살아 있었고, 기존 `t1411-campaign.py` 감독은 없었다. 마지막 관측은 켬485날·끔495날, 체크포인트는480·490날이었다. 세계가 살아 있으므로 그대로 진행시키고 감독만 다시 연결했다. 이때 세계 재생·체크포인트 되감기는0회이며, 기존 환경 중단3회의 팔별 복구 이력도 그대로 유지했다.

`preflight.json`은 살아 있는 래퍼의 PID·커널 시작 시각과 그 자손인 실제 존 두 개의 신원이다. `campaign-before.json`·`campaign-after.json`에서 래퍼 PID와 기존 복구 이력이 같음을 확인했다. 새 감독48522는 분리된 세션으로 시작했다(`launcher.json`). 현재 세계·진행 장부·실행 조건·고정 제품 및 관찰기 소스는 수정하지 않았다.

`scripts/t1411-reattach.py --check`는 게이트·지문·소스 해시·살아 있는 래퍼 명령·시작 시각·부모 관계를 읽기 전용으로 검사한다. 감독이 이미 있으면 상태를 쓰기 전에 거절한다. 실제 연결 뒤의 중복 접속 거절과 캠페인 바이트 불변은 `duplicate-check.json`에 있다.

연결된 감독은 기존 래퍼의 실제 `.exit.json`을 읽고 완료/실패를 기록한다. PID가 사라지거나 재사용됐는데 종료 증거가 없으면 감독 오류를 기록하며 살아 있는 세계를 종료하지 않는다. 기존 팔이 끝난 자리에만 원래 네 팔 대기열을 고정 계측기로 이어 붙여 실제 세계 둘 제한을 유지한다. 관측된 종료 결과가 있는 팔은 다시 실행하지 않는다.

`offline-check.py`는 실제 프로세스 목록을 빈 가짜 목록으로 바꾼 오프라인 입력1개이며 시뮬레이션을 실행하지 않는다. 가짜 종료 코드7·120날 미완료를 그대로 보존했고, 실제 종료 결과가 있는 여섯 가짜 팔을 다시 띄우지 않는지 확인했다. 이 입력은 실제730날 여섯 판이나 추가 게이트 통과로 세지 않는다.

```sh
python3 scripts/t1411-reattach.py --root /tmp/t1411 --repo /workspace/Mini --check
python3 계측/T1411_2026-11-21/controller-reattach-1123/offline-check.py
```

감독이 이미 실행 중이면 첫 명령이 거절되는 것이 정상이다. 새 감독은 Node22 환경을 물려받는 분리된 세션으로 띄우며, 백업·집계 감독이 이미 살아 있으면 중복으로 띄우지 않는다.
