## T14. ★★2026-09-01 — `e2e-mtfoot` ⑤ **종결**: 하네스가 틀렸다(렌더 무접촉)

2026-08-26 러너 통합 이후 **다섯 배치가 "기지 결함"으로 지나친** 빨간 판정을 닫았다.
`회부_기슭_평탄판정.md` 의 진단을 이 배치가 **실측으로 재확인**했고, 결론은 그 문서 §4 의 **1번**이다.

### 귀속 — 렌더가 아니라 판정이 틀렸다

```
  판정  ok('⑤ 기슭은 산보다 납작하다', mf < mm * 0.72)      mf=기슭 vy 중앙 · mm=산(L/M) vy 중앙
  실측  산 186장 중 하한 MT_VY_MIN(0.30) 에 **눌린 것 79장 = 42%**
        서 있는 산 107장 중앙 1.007  ·  전체(쌍봉) 중앙 0.450  ·  기슭 58장 중앙 0.337 [0.252~0.407]
        비:  옛 분모 0.750 (✗)   새 분모 0.335 (○ · 문턱 0.72)
```

`_mtFitVy`(`public/client/10-r1-terrain.js`)가 스프라이트 실루엣을 바위 마스크에 묶으면서 산의 42%를
하한에 **눌러 놓는다**. 눌린 산은 "서 있는 산"이 아니라 **이미 납작해진 산**이다. 그것들을 분모에 넣으면
"납작한 것보다 납작한가"를 묻게 되고, 그건 아무것도 안 재는 것이다. 게다가 쌍봉의 중앙값은 눌린 비율이
몇 %만 움직여도 0.30 쪽과 1.0 쪽 사이를 널뛴다 — **가장 불안정한 통계 위에 고정 문턱을 얹은 판정**이었다.

### 무엇을 고쳤나 — `scripts/e2e-mtfoot.js` **한 파일뿐**

* 분모를 **서 있는 산**(`vy > MT_VY_MIN + ε`)으로 바꿨다.
* **문턱 0.72 는 한 자리도 안 건드렸다.** 문턱 조정은 원인을 안 고치고 바를 낮추는 것이다(회부 §4-3 이 권하지 않는다).
* 하한 상수는 **렌더 정본에서 정규식으로 읽는다**(⑤-0). 상수를 베끼면 다음에 렌더가 바뀔 때 조용히 낡는다 —
  못 읽으면 그 자리에서 실패한다.
* 판정 셋이 늘었다: `⑤-0`(정본에서 읽었나) · `⑤-a`(분모가 정말 쌍봉인가 — 눌림 0 이면 가를 이유가 없다) ·
  `⑤-b`(음성 대조 — 기슭 vy 를 부풀리면 **×2.15 에서 ✗** 가 난다. 여유가 유한하다는 증거).
* 분포 한 줄을 판정 옆에 찍는다 — 다음 사람이 이 수를 다시 재지 않게.

```
  before  8/9   (⑤ ✗ — 기슭 0.34 < 산 0.45 의 72%)
  after  12/12
  다른 산 하네스 전원 유지: e2e-mountain 29/0 · mtcut 26/26 · mtocc 18/18 · mtcorridor 15/0 · mtfuzz 10/10
```

★**클라 파일은 한 줄도 안 고쳤다**(`git diff --name-only` 에 `public/` 0건). 렌더는 처음부터 설계대로였다 —
눌리지 않은 산과 견주면 기슭은 3분의 1 높이다.

### 남긴 관측 (수리 아님)

`10-r1-terrain.js` 의 `MT_FIT_TOL = 2.0` 주석이 "하한눌림 0%"라고 적어 두었는데, `_mtFitVy` 쪽 눌림은

pull 전 HEAD 를 믿으면 지난 배포가 도중에 실패했을 때 빠뜨린다.

## 3-산-ⓐ. ★2026-08-26 **픽셀 절단 v4 — 수직 평면** (재민 확정 · 흐림 명세 완결)

### 왜 v3(화면 평행 평면)에서 바꿨나

v3 는 **화면과 평행한 평면**(깊이 `s + 32h`)으로 잘랐다. 기하적으로는 정확히 작동했지만,
카메라가 비스듬히 내려다보므로 그 평면은 **캐릭터 머리 위로 뒤로 기울어져** 있다. 그래서
발자국이 내 뒤인 산이라도 충분히 높으면 봉우리가 그 평면을 뚫고 나와 "앞"으로 분류됐다 —
**나를 절대 못 가리는 산이 흐려졌다**(실측: 그런 띠가 v3 에서 **432장**).

**나를 가릴 수 있는 산은 정확히 무엇인가** — 한 줄로 증명된다:
산 조각이 내 스프라이트 화소에 오려면 `화면y = s − 32h` 가 내 화면y 와 같아야 하는데,
발자국이 내 뒤(`s < 내 s`)면 `h < 0` 이어야 해서 **불가능하다**.
⇒ 그 집합을 정확히 가르는 면은 **캐릭터 행을 지나는 수직 평면**(`s = 내 s`)이다.
두 평면 다 캐릭터 점을 지나는 유일한 평면이고 **지면에서는 같은 가로줄**을 지난다 — 차이는 산 위에서다.

**덤**: 화가 알고리즘의 그리기 순서도 지면 `s` 기준이라, 수직 평면으로 바꾸면 v3 가 남긴
"명세는 깊이인데 순서는 지면 z"라는 어긋남이 **소멸한다**. 흐림과 순서가 같은 자를 쓴다.

★교훈: **직관 둘("화면 평행 평면으로 자른다" · "날 못 가리는 건 불투명")이 충돌하면 진짜 의도부터 정하라.**
이 카메라에서 둘은 다른 답을 낸다.

### 경계식

```
화면 y = s − 32h                    (그리는 식)
⇒ 지면 깊이 s = 화면y + 32h
v4(채택) 판정 s > c   ·  경계 = **화면y = c − 32h**   ← 지형 따라 올라가는 등고선
v3(반례)  판정 d > c  ·  d = 화면y + 64h · 경계 = 화면y = c − 64h
```

h=0 에서는 **곧은 가로줄**(두 안이 여기선 같다). 문턱 `c = 내 지면 z + 32`(`MT_FADE_ZOFF`, 채택값 유지).

`__simvilCells`·`__claimCells`(그리고 각 `__*Probe`) 넷은 **`11-r1-mountain.js` 훅 절 한 자리**에서
선언한다. 렌더 루프(`34-m-renderloop.js`)는 프레임마다 **비우기만** 한다.

T57 이 `__claimCells` 를 렌더 루프 안에서 게으르게 만들었다(그 카드의 접촉 파일이 거기뿐이라서다).
그러면 같은 모양의 훅이 두 파일에 흩어지고 **한쪽만 고치면 조용히 어긋난다.**
`e2e-charsprite ⓖ` 가 소스를 훑어 "선언이 파일 하나에만 있다"를 검사한다.

⚠**선언은 `Object.assign` 두 줄이다.** 분할 규약이 "새 최상위 실행문은 `99-main.js` 에만"이고
`test-client-globals ③` 이 **총계 일치**를 본다. 종전 두 줄을 두 줄로 바꿔 총계를 그대로 뒀다 —
훅을 늘리려고 실행문 예산을 늘리지 않는다(그 예산은 다른 규약이 지키는 것이다).

## `__w2s` 는 NaN 을 내지 않는다 — 이름이 계약이다 (T70)

T57 이 "카메라 상태를 타는 듯"이라며 `__s2w` 를 세 점에서 재 뒤집어 쓰는 우회를 넣었다.
**재현 조건은 카메라가 아니라 키 이름이었다:**

```
  __s2w(px, py)  →  { wx, wy }      화면 → 월드
  __w2s(wx, wy)  →  { px, py }      월드 → 화면
```

T57 코드가 `.x`/`.y` 를 읽었고 둘 다 없는 키라 `undefined − undefined = NaN` 이 됐다.
`e2e-zoom`·`e2e-onboarding` 은 처음부터 `.px`/`.py` 를 읽어 멀쩡히 돌고 있었다 — **훅은 성했다.**
⇒ 이름이 자기를 말한다(w=월드 · p=픽셀). 우회는 걷었고, `e2e-charsprite ⓖ` 가 세 점 왕복으로
"유한값 3/3 · 왕복 오차 0.000px"을 상시 검사한다.
