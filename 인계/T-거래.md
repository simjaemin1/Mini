## T60. ★★2026-09-03 — **캐러밴 시계는 다섯 자리가 한 규약이다** (ECON 수술 1.5 · PM 승인)

> 전문 `보고/T60_2026-09-03.md`. 하네스 `scripts/test-msy.js` ⑤(다섯 자리 전부 소스 계약).

**무엇이 틀려 있었나** — 캐러밴이 늦어지면 `arriveDay`·`returnArriveDay` 는 밀었는데
**`travelDays` 는 안 밀었다**. `travelDays` 는 `tradeLog` 가 적는 "이 짐이 며칠 걸렸나" 라서,
그 값만 늦어짐을 모른 채 남았다. T17 이 econ 쪽 두 자리를 고쳤고, T60 이 **존 서버 세 자리**를 마저 고쳤다.

```

      if (phase === 'outbound') { c.arriveDay += days; c.returnArriveDay += days;
                                  if (Number.isFinite(c.travelDays)) c.travelDays += days; }
      else                      { c.returnArriveDay += days; }   // 귀로 지연은 가는 구간을 안 건드린다

    ⓐ 로컬 우회 재경로   _clockPush(c, pushed, body.phase)
```

export 한 줄에도 걸린다. `server/rumor.js` 는 "한 줄 거울 + 교차 계약 검사"로 버틴다(회부 유지).

★**기준선 무영향**: `travelDays` 를 읽는 곳은 `tradeLog` 와 하네스뿐이라 궤적을 안 바꾼다 —

## 3-u. ★★2026-08-27 배치 — **마을 거래소: 플레이어 물물교환**

> 재민 원문: *"마을마다 거래소가 있어서 거기서 모든 경제학이 계산되고 npc끼리 교역하잖아 —
> 거기서 플레이어도 물물교환할 수 있어야 해."*
> 제1 규약: **가격 사본을 만들면 그 순간 실패다.** 가격 반응은 **공짜다** —
> 재고가 움직이면 시세는 저절로 따라온다. "가격 갱신" 코드를 짜고 있다면 사본을 만들고 있는 것이다.

### ★§0 인벤토리 — 지시서 전제와 다른 게 둘이었다

1. **곡식(`food`)에는 플레이어 아이템이 없다.** 곳간 대응표(`PV_DEPOSIT_MAP`)가 정본인데
   `food` 를 가리키는 아이템이 한 개도 없다. ⇒ 지시서의 "물고기→**곡물**"은 **문자 그대로는 실행 불가**다.
   대신 두 뜻을 다 지켰다: **표시는 곡식 환산**(`PRICE_NUMERAIRE=food`)이고 **내는 건 물고기**다.
   받을 품목은 그 마을 시세표에서 **살아 있는 것**을 하네스가 골라 쓰고 무엇을 골랐는지 로그에 남긴다.
   (회부 B-2 — 곡식을 들 수 있게 할 것인가.)
2. **물리 상한 부품이 `events.js` 안에 인라인**돼 있었다(B-1 배치). 두 벌을 만들지 않으려고
   **`events.payableQty(stock, frac)` 로 추출**하고 게시판 보상도 그 함수를 쓰게 바꿨다 —
   한쪽만 고쳐질 길이 구조적으로 없다(`test-trade ①` 이 양쪽 소스를 다 확인한다).

### 무엇이 생겼나

### ① 교환비 = 정본 그림자가격의 비율 (사본 0)

* 값은 `econV2.computeShadowPrices(v)` **한 함수**에서만 온다. `trade.js` 에는
  가격을 계산하는 줄이 **하나도 없고**, `computeShadowPrices` 를 직접 부르지도 않는다(접근자만).
* 마을이 살 땐 `p×(1−s)`, 팔 땐 `p×(1+s)`. **`TRADE_SPREAD` s = 0.10** 채택.
  근거 ⓐ 왕복 무한 차익 봉쇄 ⓑ "교역 세금 = 물물" 캐논의 플레이어 판(마진은 **물자로** 마을에 남는다).
* **물리 상한**: 한 거래가 그 품목 재고의 `TRADE_STOCK_FRAC`(=`EV_REW_STOCK_FRAC` 0.25)을 못 넘는다.
  넘치면 **거절이 아니라 절삭**이다(살 수 있는 만큼은 산다).

### ② ★★조각 적분(`planSliced`) — 하네스가 잡은 진짜 결함

1차 실장은 **거래 전 시세로 전량**을 계산했다. `test-trade ②`(스프레드 0 대조군)가 잡았다:
**나무 14 → 돌 45 → 나무 18.** 없던 나무 4개가 생겼다.
원인: 내가 팔면 그게 싸지고 사면 그게 비싸지는데, 되팔 때 **두 다리가 둘 다 유리**해진다 —
내 거래가 만든 가격 변화를 내가 그대로 주워 먹는다(한 번에 재고의 25%를 움직이니 폭이 s=10%보다 크다).
⇒ **곡선을 따라 적분**한다. 거래를 12조각으로 나눠 조각마다 **그때의 시세**로 값을 매긴다.
지금: s=0 에서 **정확히 본전**(19→46→19), s=0.10 에서 왕복 **−30%**.
※ 견적의 `maxGive` 는 곡선이라 나눗셈으로 못 내서 **이분 탐색 24회**로 낸다.

### ③ ★★가격 반응이 화면에 보이는가 — `e2e-trade ⑤` 가 잡은 것

**하루 캐시를 쓰고 있었다.** `board/quote` 가 `Events.pricesOf`(=`v._priceCache`, NPC 교역 틱이
**하루 한 번** 덮는 값)를 봐서, 같은 날 안에서는 재고가 어떻게 움직여도 같은 값을 돌려줬다.
별도 프로브 실측(캐시 warm → 날 얼림 → 대량 매도):

```
  나무  재고 19.95 → 26.95 (+35%)   표시 1.208 → 1.208   견적가 2.734022 → 2.734022
  돌    재고 150.26 → 116.26 (−23%) 표시 0.161 → 0.161   견적가 0.363397 → 0.363397
  해동 후 하루:                      표시 1.208 → 1.098   ← 그제서야 움직인다
```

결과가 둘이었다 — ⓐ **이 배치의 존재 이유가 화면에서 사라진다**(첫 30분 ② "내가 판 물건에 값이
움직인다") ⓑ **표시된 비율과 실제 수령량이 갈린다**(수령량은 `planSliced` 가 지금 재고로 낸다).
⇒ 거래소가 보는 시세는 **지금 재고의 함수**다. 하루 캐시는 NPC 교역 틱의 **성능 장치**일 뿐
정본의 정의가 아니다. `Events.pricesFresh` 로 고쳤다.
⚠**econ 변경이 아니다** — NPC 교역은 종전대로 제 하루 캐시를 읽는다(그 경로는 한 줄도 안 건드렸다).
플레이어가 움직인 재고는 다음 날 캐시가 다시 계산될 때 NPC 쪽에도 그대로 반영된다.

같이 잡힌 것: **표시를 `toFixed(3)` 으로 하고 있었다.** 한 마을 안 시세가 47.79 부터 0.0047 까지
걸치는데 소수점 고정이면 싼 쪽 네 품목이 화면에서 전부 "0.005"로 **같아 보인다**.
⇒ **유효숫자 4자리**로 바꿨다. 값이 같아 보이는 표는 정보가 아니다.

### ④ ★계측기가 자기 눈을 가린 사례 **세 번** — 전부 하네스 결함이었다

⑤는 **네 번 만에** 통과했다. 첫 실패만 제품 결함(위 ③)이고 **나머지 셋은 계측기**였다. 셋 다 남긴다:

* **ⓑ 가격 바닥을 골랐다.** `computeShadowPrices` 는 희소도를 `PRICE_ADJ_MIN..maxAdj` 로 **클램프**한다 —
  과잉 재고 품목은 바닥에 붙어 **재고가 늘어도 값이 안 움직인다**(글럿 바닥의 존재 이유 그 자체).
  1차 하네스는 "마을이 팔 수 있는 양이 가장 많은" 품목을 골랐는데 그건 곧 **가장 과잉인 품목**이라
  바닥일 확률이 가장 높은 선택이었다. **자기가 못 움직일 걸 골라 놓고 "안 움직인다"고 보고했다.**
* **ⓒ 두 판정을 한 짝에 묶었다.** "판 것 ↓ **그리고** 산 것 ↑"을 한 짝에서 동시에 요구했더니,
  러너 실행에서 `가죽→고기` 의 가죽이 **0.03226 → 0.0164 로 반토막 났는데도** 고기가 바닥이라 전체 실패였다.
  ⇒ 판정을 쪼개고 **각자 후보를 순회**하게 했다.
* **ⓓ 거래가 안 일어난 걸 "값이 안 움직였다"로 읽었다.** 받을 것 후보 6종이 전부
  `재고 10.41 → 10.41` 이었는데, 그건 **교환이 거절당한 것**이었다(비싼 물건을 내려는데 마을이
  값을 못 치르면 거절된다). 게다가 **실패엔 서버가 시세표를 다시 안 보내니 화면도 그대로**라
  "아무것도 안 변했다"와 구별이 안 된다. ⇒ `push()` 가 **성사 건수를 재고 변화로** 세고(알림 링버퍼는
  40칸이라 못 믿는다), 0 이면 서버 거절 문구를 찍은 뒤 다음 후보로 넘어간다.
  짝을 고를 때 **마을이 값을 치를 수 있는지**(`재고상한 × 시세 > 한 개 값 × 1.3`)를 먼저 본다.

지금 하네스는 후보를 순회하며 **실측으로** 고르고, 어떤 짝으로 성공했는지·건너뛴 이유·거절 문구를
전부 찍는다. 독립 2회 실행이 **서로 다른 마을 상태에서 각각 40/0**:
`나무 1.568→1.199`(팔았다) · `1.199→1.395`(샀다) / `약초 1.064→0.7309` · `0.7309→0.8148`.

### ⑤ 정보 비대칭 · 게시판 우위 · 금지 품목

* **원격 시세 조회 API 를 안 만들었다.** `board/quote/exec` **셋 다** 첫 줄이 `_villageNear`(260px,
  브리핑과 같은 게이트)다 — 이웃 마을 시세는 **걸어가서 보는 것**이고 그 비대칭이 콘텐츠다(§3.2).
  `test-trade ⑦` 이 3/3 을 구조로, `e2e-trade ①` 이 **클라 우회 시도**로 확인한다
  (vid 를 알고 직접 물어도 거절 · 읽기만 막고 쓰기를 여는 실수도 따로 확인).
* **게시판이 늘 낫다**: ×1.200(프리미엄 0.2) > ×0.818(스프레드 0.1). 둘 다 실제로 걸려 있음도 확인.
  (게시 시점 고정이라는 단서는 회부 B-7.)
* **잠긴 품목**: 열린 의뢰가 **보상으로 약속한 품목**은 마을이 안 판다 — 안 그러면 플레이어가 낸 뒤에
  "갚을 게 없다"를 듣게 된다(게스트보상 배치의 족보). 내부 필드(`_` 로 시작)도 재화가 아니다.
* **원자적**: ①견적 ②**재고를 먼저 잡는다** ③내 물건 차감 ④곳간 입고(정본 `playerVillageDeposit`)
  ⑤실패하면 되돌린다. 동시 경쟁은 ②가 관문 — 둘이 같은 마지막 재고를 못 가져간다(실측 확인).

### ⑥ 화면 — §8 프레임의 **둘째 칸**

패널을 새로 만들지 않았다. 3-v 가 세운 프레임에 **탭 하나**를 등록했다(그 3단계가 문서대로 돌아가는지의 실증):
`#sidebar` 아이콘 한 줄 + 제목표 한글 + `renderSide` 분기. **Shift+T.**
문법은 세 클릭 — 📤 낼 것 → 📥 받을 것 → **바꾼다**. 수치는 전부 서버가 준 것을 그대로 그린다.
열 때 **서버에 다시 물어본다**(클라가 시세를 캐시하면 그게 곧 낡은 시세다).
