## 1. ① 승계 — 등록하는 순간 소유를 잃던 역설

### 무엇이 이상했나
배치 13 으로 게스트가 마을을 세우고 재접속해도 제 것이 됐다. 그런데 **그 게스트가 계정을 만들면**
`/auth` 가 `player_id = username` 인 **새 행**을 만들었다. playerId 가 바뀌니
사유지(`ownerPid`)·건물(`ownerId`)·노(`data.owner`)·마을(`founder`)이 **한꺼번에 남의 것**이 됐다.
영속 신원을 만든 보람이 **등록하는 순간 사라지는** 역설이다.

### 어떻게 고쳤나 — 행을 갈아치우지 않는다

```
POST /promote { token, username, password, … }
   └─ 게스트 토큰으로 그 행을 찾는다(비밀번호 없는 행만)
   └─ UPDATE players SET name=?, password_hash=?, password_salt=?, guest_token=NULL … WHERE player_id=?
                                                                    ▲
                          player_id 는 **손대지 않는다** — 그게 곧 소유 불변이다
```

**승계와 동시에 게스트 토큰이 죽는다**(`guest_token = NULL`). 배치 13 의 *"비밀번호가 생긴 행은
게스트 토큰으로 못 연다"* 게이트와 **벨트와 멜빵**이다 — 한쪽이 뚫려도 다른 쪽이 막는다.
클라도 `welcome.promoted` 를 보고 localStorage 의 죽은 토큰을 지운다(세 번째 벨트).

### ★거절 사유를 둘로 가른 것이 이 경로의 안전핀이다

| 사유 | 뜻 | zone 의 처리 |
|---|---|---|
| `username_taken` | 그 이름이 **남의 계정**이다(비밀번호가 안 맞는다) | **막는다** |
| `not_promotable` | 승계할 게 아니다(토큰 무효 · 이미 계정 · **그 이름이 내 기존 계정**) | **막지 않고** 평소 로그인으로 흘린다 |

후자가 없으면 사고가 난다: 옛 게스트 토큰이 남아 있는 브라우저에서 **기존 계정으로 로그인**할 때
"이름 중복"으로 **제 계정에 못 들어가게** 된다. 하네스가 그 경로를 명시적으로 검사한다.

### 딸려 온 것 — 이제 `player_id ≠ name` 인 계정이 처음 생긴다

종전엔 등록 계정의 `player_id === name` 이라 "이름으로 찾기"가 곧 PK 조회였다. 승계 계정은
`player_id = anon_…`, `name = 사용자이름` 이다. ⇒ 두 곳을 정본 술어 하나(`findAccount`)로 바꿨다:

* **`/auth` 로그인 조회** — PK 조회만 하면 승계 계정으로 **영영 로그인할 수 없다.**
* **`/check_username` 중복 검사** — PK 조회만 하면 승계된 이름을 **비어 있는 것으로 오판**해
  같은 이름을 두 번 내준다. (지시가 말한 *"기존 `/check_username` 그대로"* 는 **같은 엔드포인트·같은
  계약**을 지킨 것이고, 질의 범위는 넓혀야 구멍이 안 남는다 — 넓히지 않으면 검사 자체가 거짓이 된다.)
* 그리고 **계정 이름에 부분 유니크 인덱스**를 걸었다(`password_hash IS NOT NULL` 인 행의 `name`).
  조회 검사와 DB 제약, 둘 다 있어야 경합에서도 안 뚫린다.

### 이름이 바뀌는 첫 사례 — 그래서 전수를 다시 돌렸다
배치 13 이 *"소유 판정에 이름을 쓰는 곳 0곳"* 을 전수로 확인했지만, **승계는 이름을 바꾸는 첫 사례**다.
그 전수를 그대로 재실행했다 — 여전히 **0곳**(`ownerName`·`owner_name`·`tameOwnerName` 은 표시 전용).

## 2. ② 몸의 영속 — 신원은 남는데 몸이 초기화되는 반쪽

`savePlayer` 의 첫 줄이 정책이었다: `playerId.startsWith('anon_')` 이면 저장하지 않는다.
배치 13 뒤로 그 접두사는 **두 종류**를 뭉뚱그린다 —

* central 이 발급한 **영속 게스트**(토큰 있음) → 저장해야 한다
* central 불가 시의 **1회용 폴백** → 저장할 대상이 아니다(다음 접속에 다른 사람이다)

접두사로는 못 가른다. ⇒ 접속 때 정해지는 `player.persistent` 하나를 보고, 판정을 **함수 하나**로 모았다:

```js
function canPersist(player) {
  if (!player || !player.playerId) return false;
  if (player.playerId.startsWith('npc_')) return false;
  if (player.playerId.startsWith('anon_')) return !!player.persistent;   // 영속 게스트만
  return true;                                                           // 등록 계정
}
```

★**호출부에 있던 사본 17곳을 걷어냈다.** 종전엔 `if (!player.playerId.startsWith('anon_')) savePlayer(...)`
가 17곳에 흩어져 있었다 — 가드 한 줄만 풀었다면 **대부분의 경로에서 게스트 저장이 조용히 안 켜졌을 것**이다.
(이 프로젝트가 반복해 만난 "사본이 정본과 어긋난다"의 전형이다.)

**복원**은 새 경로를 안 만들었다. `/guest` 가 그 게스트의 **행 전체**를 함께 주고, zone 은
등록 계정과 **완전히 같은 복원 블록**을 탄다 — 그러려고 접속 핸들러를
`신원 해석(분기) → 공통 복원(한 곳)` 으로 재구성했다. 게스트 전용 테이블도, 전용 경로도 없다.
*이제 게스트는 "비밀번호 없는 계정"일 뿐이다.*

⚠**존을 넘어도 이어진다** — 핸드오프 페이로드에 `persistent` 를 실었다. 접두사만으로는
받는 존이 영속 게스트를 1회용으로 오판해 저장을 끊었을 것이다.

## 4. 스키마·계약

| | |
|---|---|
| `POST /promote` (central) | `{token, username, password, color?, home_*}` → `{ok, player}` · `{ok:false, reason}` |
| `players` 부분 유니크 인덱스 | `name` WHERE `password_hash IS NOT NULL` (승계로 생기는 이름 충돌 차단) |
| `POST /guest` | 응답에 **`player`(행 전체)** 추가 — zone 이 등록 계정과 같은 경로로 몸을 복원 |
| `welcome.promoted` | 이번 접속에서 승계가 일어났나 — 클라가 죽은 토큰을 지운다 |
| 핸드오프 `persistent` | 존을 넘어도 저장이 이어진다 |
| `canPersist(player)` | 저장 대상 판정 **정본**(호출부 사본 17곳 제거) |

**되돌리기·호환**: central 이 `/promote` 를 모르면 zone 이 예외를 먹고 **평소 `/auth`** 로 흘러간다
(= 배치 13 동작). `/guest` 가 `player` 를 안 주면 몸 복원만 꺼지고 신원은 그대로다.
⇒ 배포 순서 제약 없음.
