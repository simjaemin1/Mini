## 1. 임수 위반 — 감사가 임수를 한 번도 안 재고 있었다

### 1.1 §0 실측 — 판정식이 무엇이었나

`audit-village-forage.js` 의 ④ 식수는 **반경 안의 `water_pool` 개체**를 센다. 그 개체는 마을 둠벙만이 아니다:
`chunk.pickResourceType` 이 **모든 biome 에서 굴림 상위 1~5%** 로 야생 물웅덩이를 깐다.

```
  plains   r ≥ 0.99 → water_pool      forest   r ≥ 0.98      mountain r ≥ 0.98
  taiga    r ≥ 0.96                   tundra   r ≥ 0.85      desert   r ≥ 0.94  …
```

⇒ 지도 어디든 960px 안에 웅덩이 하나쯤 걸린다. **강에서 10,848px(도보 2분 50초) 떨어진 광산1 이
"식수 합격"** 이었다. 못 떨어지는 판정은 판정이 아니다(`인계/공통.md` §2 자명 통과 금지).

★그리고 **처방 스크립트(`plan-village-forage.js`)가 같은 셈**을 쓴다 — 그래서 2026-08-29 배치가
그 다섯 마을을 "물 있음"으로 읽고 **건너뛰었다**. 감사와 처방이 같이 눈이 멀어 있었다.

### 1.5 ★고치면서 드러난 결함 둘 — 둘 다 이 배치가 닫았다

**ⓐ 처방 스크립트가 멱등이 아니었다.** 머리말은 *"다시 돌리면 같은 결과가 나온다"* 고 적어 두었는데,
`measure()` 가 **자기가 심은 군락까지 세기 때문에**(청크 생성기가 groves 를 실체화한다) 두 번째 실행은
"부족한 마을 0곳"을 낸다.

```
  실측(손대기 전, 그냥 실행):   ── 군락 0개 · 개체 총 0개
  ⇒ --apply 했으면 groves 48개가 통째로 사라졌다.
```
수리: 측정을 **자연 상태**(groves 를 걷어 낸 세계)에서 한다(`withoutGroves` — 청크 캐시도 비운다).
그리고 **줄어들면 멈추는 가드**(`--allow-shrink` 없이는 종료). 두 번 돌려도 53개다(확인).

**ⓑ 군락 배열은 순서가 계약이다.** `chunk.js` 가 `seedKey` 를 **배열 인덱스**로 만들고
(`gv<gi>_<i>`) `harvested_seeds` 가 그 문자열로 "이미 캤다"를 기억한다.

```
  실측(그냥 다시 쓰면):  옛 군락 48개 **전부** 인덱스가 밀림 · 그중 채집 대상 28개(= 84 seedKey)
  ⇒ 캤던 덤불이 되살아나고 안 캔 덤불이 사라진다(라이브 DB).
```
수리: `keepOrder()` — 옛 배열을 앞에 그대로 두고 새것만 뒤에. **접두 검사**로 증명하고 어긋나면 종료.
```
  → 적용: server/hanbando-terrain.json 의 groves = 53개  (옛 48개는 인덱스 그대로 · 새 5개는 뒤에 붙임 — seedKey 불변)
  검증: 접두 48개 완전 동일 = true · groves 외 지형 키 전부 동일 = true
```

### 1.6 샘은 민물이다 — 바다 가드와 그 **대조군**

`fits('water_pool')` 은 `ctx.isWater`(강·호수)만 봤고 **해안선 띠는 안 봤다**. 바닷가 마을의 링 자리가
바다 위로 잡힐 수 있었다 — "민물 샘"이라 적고 짠물을 심는 것이다. ⇒ 중심 + 반경 12방위를 `isSea` 로 검사.

★**대조군(자명 통과 방지)**: 가드를 끄면 **어촌6 의 자리가 바다 한복판**(중심 true · 반경 true)으로 잡힌다.
가드가 실제로 무언가를 막는다는 증거다. 심은 5곳은 가드 유무와 무관하게 같은 자리 — **예방 장치**다.

### 1.7 어귀 링 형식 — 불변 확인 (온보딩 v2 와의 계약)

`village-layout.js` 의 `ditchRing()` 반환 형식(`{cells, gates, a, b, ao, bo, frame, …}`)과
`DITCH_GATE_HALF` 를 **한 글자도 안 고쳤다.** `groves` 항목 형식(`{name, vil, kind, center, r, n}`)도 그대로.
★관측 하나를 회부로 넘겼다: **환호(어귀)는 시범 마을에만 있다** — "어귀 링에서 빈터 구역 산출"을
글자 그대로 쓰면 대부분 마을에서 안 나온다. 대안은 `territoryBoundary` 경계 링.

## 2. `e2e-mtfoot` ⑤ — 하네스가 틀렸다

### 2.1 귀속을 먼저 갈랐다

```js
ok('⑤ 기슭은 산보다 납작하다', mf < mm * 0.72)     // mf = 기슭 vy 중앙 · mm = 산(L/M) vy 중앙
```
```
  실측(재현)  산 186장 중 하한 MT_VY_MIN(0.30) 에 **눌린 것 79장 = 42%**
              서 있는 산 107장 중앙 1.007 · 전체(쌍봉) 중앙 0.450 · 기슭 58장 중앙 0.337 [0.252~0.407]
              비:  옛 분모 0.750 (✗)   새 분모 0.335 (○)
```

`_mtFitVy`(`public/client/10-r1-terrain.js`)가 스프라이트 실루엣을 바위 마스크에 묶으면서 산의 42%를
하한에 **눌러 놓는다**. 눌린 산은 "서 있는 산"이 아니라 **이미 납작해진 산**이다. 그걸 분모에 넣으면
"납작한 것보다 납작한가"를 묻게 되고, 그건 아무것도 안 재는 것이다. 게다가 쌍봉의 중앙값은 눌린 비율이
몇 %만 움직여도 0.30 쪽과 1.0 쪽 사이를 널뛴다 — **가장 불안정한 통계 위에 고정 문턱을 얹은 판정**이었다.
⇒ **렌더가 아니라 판정이 틀렸다.** `회부_기슭_평탄판정.md` §4 의 **1번**이 이 결론이고, 이 배치가 실측으로 재확인했다.

### 2.2 고친 것 — `scripts/e2e-mtfoot.js` 한 파일

* 분모를 **서 있는 산**(`vy > MT_VY_MIN + ε`)으로.
* **문턱 0.72 는 한 자리도 안 건드렸다.** 문턱 조정은 원인을 안 고치고 바를 낮추는 것이다(지시서 금지 · 회부 §4-3 도 권하지 않는다).
* 하한 상수를 **렌더 정본에서 정규식으로 읽는다**(⑤-0). 못 읽으면 그 자리에서 실패한다 — 상수를 베끼면 조용히 낡는다.
* 판정 셋이 늘었다:
  * `⑤-a` 분모가 정말 쌍봉인가(눌림 0 이거나 서 있는 산 0 이면 이 판정을 가를 이유가 없다).
  * `⑤-b` **음성 대조** — 기슭 vy 를 부풀리면 **×2.15 에서 ✗** 가 난다. 통과가 여유 때문이 아니라 사실 때문이라는 증거.
  * 분포 한 줄을 판정 옆에 찍는다 — 다음 사람이 이 수를 다시 재지 않게.

### 2.3 결과

  after   12/12
  [⑤ 분포] 산 186장 중 하한(0.3) 눌림 79장(42%) · 서 있는 산 107장 중앙 1.007
           · 전체(쌍봉) 중앙 0.450 · 기슭 58장 중앙 0.337 [0.252~0.407]
