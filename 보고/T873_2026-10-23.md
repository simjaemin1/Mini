## 1. 두 벌이 어디였나(T868 회부 3)

* **일반 접속**(`_acceptConnection`): 몸 칸이 네 군데에 흩어져 있었다 — 복원 버퍼 선언(`_loadEquipment` … `_loadMember` · `initVital` · `tools` 감싸개) → 토큰 블록 · 로그인 블록이 버퍼마다 한 줄씩 채움 → 리터럴 앞 감싸개 풀기(`_toolItems` · `_hotkey1`) → 리터럴의 몸 칸 열아홉 줄(신체 빈 칸 0 채움 · 생명값 넷 포함).
* **승격**(`promote_to_primary` · T868 켬): `_t868BodyInto(p, B)` 가 같은 열아홉 칸을 제 차례로 다시 적었다.
* 몸에 칸이 새로 생기면 `serializeBody` · `parseBody` 말고도 **두 목록**을 다 받아야 했다(T47 "직렬화가 한 함수다"의 남은 틈).

## 2. ① 고침 — `_bodyInto` 한 자리(손잡이 없음 · 같은 값 · 같은 칸)

```js
function _bodyInto(p, B, equipped) {
  p.toolItems = B.toolItems; p.equipped = equipped; p.hotkey1 = B.hotkey1;                 // 종전 리터럴 차례 그대로
  p.equipment … p.craftSkill · p.craftLog · p.oreLedger · p.oreCarry · p.fishStats · p.kgLedger · p.lots
  p.body = B.body ? { cold: 0, fatigue: 0, injury: 0, morale: 0, herbUntil: 0, stages: {}, ...B.body } : null;
  p.lastSeenDay · p.member · p.hp · p.maxHp · p.isDown · p.downedAt                          // 생명값은 몸에 있을 때만(없으면 최대 · 일어선 채)
  return p;
}
```

* **일반 접속**: 버퍼는 `_B` 하나다(`parseBody` 의 꼴 그대로 · 기본값 `parseBody({}, { vitals: true })` = 종전 버퍼 기본값과 같은 값). 토큰 블록은 `_B = _hb.B` · 로그인 블록은 `_B = parseBody(행 몸, { vitals: true })` 한 줄이다. 리터럴은 몸 칸 열아홉 줄 대신 펼침 한 줄이다. 펼침이라 그 자리에 종전 차례 그대로 꽂힌다(사람 객체 키 차례가 종전과 같다 — §3).
* **승격**: `_t868BodyInto(player, _t868hb.B)` → `_bodyInto(player, _t868hb.B, _t868hb.B.equipped || pending.equipped || null)`. 장착 출처는 토큰 경로와 같은 글자다(몸 → 페이로드 → null). 승격 리터럴에 이미 있는 칸(장착 · 장비 · 슬롯 · 숙련 · HP)은 제자리에 덮이고, 새 칸은 종전 `_t868BodyInto` 와 같은 상대 차례로 붙는다.
* **장착(`equipped`)만 부르는 쪽이 정한다** — 길마다 출처가 다르다: 토큰 · 승격은 몸 → 페이로드, 로그인은 행 칸(`acct.equipped`), 처음 온 사람은 null. 로그인 블록의 `if (_B.equipped) equipped = _B.equipped;` 는 몇 줄 아래 `equipped = acct.equipped || null` 이 늘 덮는 줄이다 — 종전 그대로 두었다(회부 ③).
* 온보딩 도착(`Onboarding.arriveFor(… , _loadLastSeenDay)`)은 `_B.lastSeenDay` 를 읽는다(같은 값).
* 칸마다 붙어 있던 주석(14.53 · 낚시 v2 · 무게 · T7 · T11 · T47)은 `_bodyInto` 의 그 줄로 옮겼다. 리터럴의 "로그아웃 후 재접속의 풀피는 정책" 주석은 T43(로그인도 `vitals:true`) 뒤로 낡은 말이라 "핸드오프 · 로그인 둘 다"로 고쳐 적었다.

## 6. 회부

1. **[정보 · T868 켬 기본 착지 뒤]** 승격 리터럴의 끔 판 몸 칸(`equipped: pending.equipped || null, equipment: [], equipSlots: {}, craftSkill: {}` · `hp/maxHp: PLAYER_MAX_HP`)과 T732 로트 줄은 T868 끔 갈래의 몫이다. 켬이면 `_bodyInto` 가 다 덮는다. T868 손잡이를 걷을 때 같이 지우면 승격 리터럴에 몸 칸이 0 이 된다(그때 ⑦ P 검사 ⓓ 의 T732 예외도 빠진다).
2. **[정보 · 셋째 목록]** 같은 존 산 몸 승계(`_takeover` — 같은 신원 새 소켓이 붙을 때 옛 몸이 메모리에 있으면 그 몸을 잇는다)는 사람 → 사람으로 칸을 옮기는 **셋째 목록**이다(이 카드 밖 · 손 안 댔다). 그 목록엔 **제작이력 · 어획 · 신체(추위 · 피로 · 부상 · 사기)가 없다** — 셋은 승계 때 산 몸이 아니라 저장본(`parseBody`)에서 온다. 저장본은 행 읽기가 승계보다 먼저라 마지막 저장 때 값이다(신체는 주기 저장 사이만큼 되돌아갈 수 있다 · 미측정). 몸에 칸이 새로 생기면 받아야 하는 자리로 남는다.
3. **[정보]** 로그인 길의 장착은 행 칸(`acct.equipped`)이 정본이다 — 몸 덩이의 `equipped` 는 읽고도 늘 덮인다(종전 그대로 · 같은 값이라 안 지웠다). 저장은 둘 다 같은 `p.equipped` 를 쓰므로(`serializeBody` · `savePlayer` 칸) 지금은 갈리지 않는다.
4. **[정보 · V8 꼴]** 키 차례 · 값은 같지만 V8 의 객체 꼴은 달라졌다. 리터럴 한가운데 펼침이 있으면 V8 은 리터럴의 정적 칸 수만큼만 객체 안 자리를 잡는다. 펼침이 그 자리를 먼저 쓰므로 뒤쪽 17칸(다운 시각 · 허기 · 갈증 · vp · 영속 · 부족 · … · `_arrivedAt` — 마을 손잡이 켬이면 `_tribe0` 까지 18칸)이 객체 밖 속성 배열로 간다. 실제 리터럴 글자를 떼어 만든 객체로 확인했다: 종전 객체 안 47자리 · 객체 밖 0칸 → 새 객체 안 29자리 · 객체 밖 17칸(둘 다 빠른 꼴 — `%HasFastProperties`). 같은 꼴 모형으로 잰 값(일곱 판 중앙값): 만들기 57 → 478 ns(+0.42 µs/접속) · 그 칸 읽기 0.64 → 0.85 ns. 사람 몸만이다(NPC 리터럴 무관 · 서버 기준선 같음). 글자 하나(펼침)와 객체 안 자리는 같이 못 가진다 — 칸을 리터럴에 다시 적으면 목록이 둘로 돌아간다.
