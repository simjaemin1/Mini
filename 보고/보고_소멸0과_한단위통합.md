## 1. ① 소멸 0 튜닝

### 1.1 먼저 — 인계 프롬프트의 진단은 **틀렸다**

인계는 "좀비 덫 3중 잠금"을 이렇게 적었다:
> 도구 0 → 맨손 ×0.25 → 하루 생산 ≈ 하루 소비 → 저장 잉여 영원히 0 →
> `tickRecovery` 게이트(저장 식량 ≥ N×15) 영영 미달 → binding 은 1·2번이다

**실측이 반증했다.** 좀비 마을은 굶지 않는다:

| 마을(시드42, 800일) | 인구 | 곳간 식량 | 국고 현금 | 캐러밴 | 식량수입 |
|---|---|---|---|---|---|
| 어촌9 | 2 | 128 | **15,186** | 61회 | 504 |
| 광산2 | 2 | 62 | **15,880** | 52회 | 883 |
| 임업3 | 2 | 36 | 1,221 | 51회 | 138 |

`tickRecovery` 의 `식량 ≥ N×15`(=30) 게이트는 **통과하고 있었다.** 잠금 ②는 binding 이 아니다.
잠금 ③(구제 캐러밴)도 아니다 — 이 마을들은 800일 동안 51~61회 캐러밴을 보내고 있었다.

### 1.2 궤적이 낸 진짜 인과

`scripts/econ-lab-real.js` 의 10일 표본에 K 3항·dP 분해·도구·석재·픽커 `need` 를 실었다.
그러자 **land.stone 이 0.25 / 0.70 / 1.87 로 전부 다른 세 마을이 같은 순서로 죽는 것**이 보였다:

```
  ① 석재 재고 189 → 0        (임업3 d120 · 어촌9 d180 · 광산2 d280)
  ② 석공이 도구를 못 만든다     (produceSpecial 재료 게이트 `stone >= 0.2`)
  ③ 도구 재고 → 0             (임업3 d280 · 어촌9 d220 · 광산2 d340) · 석공 수 → 0
  ④ 전 직업 생산 ×0.25(맨손) → prodK 붕괴 (임업3: 61 → 19)
```

⑦의 좀비 마을 K 분해: **slot 121~203 · fuel 42~2,450 · prod 0.1~2.9.**
땅은 멀쩡한데 K 정의가 마을을 죽이고 있었다.

#### STONE_NET (`sim/economy-sim.js`)

#### PRODK_CAP (`sim/economy-sim.js`)
`prodK` 를 **용량 기준**으로 — `fuelK` 와 완전 동형:
```
  fuelK: (벌목 자리 × base × land.wood) ∧ woodSustain + 볏짚 + 수입EMA + 재고/90
  prodK: (농·어·렵·채집 자리 × base × landBoost) ∧ {fish,forage}Sustain + 수입EMA
```
리비히 min 세 항 중 `slotK`·`fuelK` 는 용량인데 `prodK` 만 실현흐름이었다. `fuelK` 는 2026-07 에

**prodK 만 마지막까지 남아 리비히 min 안에서 홀로 N 을 따라다녔다.**

보수적 하한을 택했다: 부산물 식량환산(연어·새우·게·굴·견과)과 도구 배수를 **뺐다**.

## 2. ② 배합↔교역 한 단위 통합 — 채택

재민: **"네가 이해한 게 맞아. 비교가 필요해. 단, 정확해야 해."**

### 2.1 (가)안을 그대로 쓰면 비교가 아니라 **새 편향**이다

설계안 (가)는 "주조식의 **재료비만** `opp` 로"였다. 그러면 투입은 수출 기회를 보는데
산출(무기)은 못 봐서, 무기가 밖에서 비싼 마을일수록 주조가 부당하게 저평가된다.
올바른 판정식은 `이윤 = (산출의 최선용도 값) − (투입의 최선대안 값)` 이라 **양변 모두** opp 여야 한다.
`_alloyMelt` 의 `price` 한 줄을 `_oppPrice` 로 바꾸면 재료비와 산출값이 동시에 바뀐다.
`_smithWeaponCost`(금속)·`_masonWeaponCost`(돌)도 함께 — 이 둘은 `_smithBeatsMason` 에서
**서로 비교되는 값**이라 한쪽만 바꾸면 그 비교가 기울어진다.

### 2.2 "정확해야 해" — 사본이 아니라 **같은 식**

`opp(r) = max(내 마을 그림자가격, 최고 순수출가)`. 순수출가는 새로 짠 식이 아니라
`tickTradeV2` 발주 EV 에서 **항을 그대로 떼어 온 것**이다:

```
  발주 EV/단위 = pTo×MARGIN×(1−TAU)×(1−기대손실) − 운반비 − pFrom×(1+TAU)
                 └──────────── netExportValue(순수취) ────────────┘
```
마지막 항은 **그 재화의 기회비용 자체**라 여기서 빼면 이중계상이다.

- **사본 금지** — v2 가 `world.netExportFn` 으로 주입, v1 이 받는다(`priceFn` 선례).
  v1→v2 역참조는 순환이라 금지. 미주입(v1 단독 CLI)이면 `_matPrice` 와 **바이트 동일** = 회귀 무영향.
- **같은 상수·같은 후보·같은 위험모형** — `FORWARD_PRICE_MARGIN` 0.95 · `TAU` · 운반비 계수 ·
  `RAID_BASE/MAX/PER_100` · `_near20 ∩ infoRange` · 발주와 같은 제외조건(인구<2·고립·포위·원한) ·
  갱 호위 충족도(`_repelP`) 보정.
- **해상도** — 하루 1회 산정 캐시. `tickTradeV2` 자신이 `a.prices` 를 사이클당 1회 산정해
  그날 발주를 전부 결정하므로 **같은 해상도**다. 더 자주 재면 교역층보다 정밀해져 정합이 아니라 불일치가 된다.

### 2.3 하네스가 못박은 것 (`test-valuechain.js` ⑥ — 신설)

숫자가 아니라 **산술의 동일성**을 검사한다. 한 항이라도 갈라지면 두 결정이 다시 따로 논다:
상수 리터럴 일치 · 각 항의 유무 · `−pFrom` 항의 **부재** · 같은 위험모형 ·
손계산과 **오차 < 1e-9** 일치 · 거리 의존(운반비·위험 항 생존) · 캐시 무해 · `opp` 가 실제로 수출가를 본다.

⚠1차 작성이 **거짓 통과**했다: 검사 상황의 순수취가 음수라 `max(0,·)` 에 뭉개져 `0 = 0` 이 됐다.
거리를 붙이고 도착지를 기근으로 만들어 **양수 상황**을 강제하고, 그 양수성 자체를 assert 로 걸었다.
(이 세션 기록 ⑱ — *틀린 하네스는 조용히 통과하지 않고 없는 결함을 보고한다*의 쌍둥이:
**틀린 하네스는 조용히 통과하기도 한다 — 검사 상황이 자명한 경우.**)

## 6. 남은 것 / 다음 사람에게

1. **라이브 DB 리셋은 재민만.** 절차는 `DB리셋_절차.md` §5. 리셋하면 위 §3 의 재시딩이 라이브에도 돈다.
2. **`ALLOY_OPP` 되돌리기**는 env 하나(`ALLOY_OPP=0`). 무기 총량 −3~8% 가 마음에 걸리면 끄면 된다 —
   대신 합금 등급이 1.21 → 0.79 로 돌아간다.
3. **TOOLBOOT·SWITCH2 는 코드에 남아 있다**(기본 OFF). 지금은 무효지만 다른 병목이 풀리면 다시 잴 값이 있다.
4. **좀비 정의**는 "최종 인구 10명 미만"으로 집계했다(`scripts/ab-summary.js`). 지금 0 이다.
5. **day365 기아사망 보호막**(`day < 365` 클램프)은 그대로 뒀다. 지금은 해제 시점에 마을이
   K 위로 과성장해 있지 않아 절벽이 안 생긴다 — 원인을 고쳤으므로 증상 완화 장치는 건드리지 않았다.
   다만 이건 **여전히 시한폭탄 형태**다(보호막이 dP<0 을 삼키는 구조 자체는 남아 있다). 회부 후보.
6. **석재 sink 의 정체는 끝까지 안 팠다.** 광산2 가 20일 만에 석재 1,280 을 잃는 구간이 있는데
   (건축 유지 `STONE_MAINT_PC` 0.02/인/일로는 27밖에 설명 못 한다) STONE_NET 이 공급 쪽을 열어
   증상이 사라져 추적을 멈췄다. 재발하면 여기부터 보면 된다.
